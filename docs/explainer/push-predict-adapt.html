Push, Predict, Adapt

What we predict, how a push becomes a table row, where the autoregressive part is, and what RL can and cannot do. Ten short animated steps, then a live simulation.

In one sentence: if the robot pushes this object from here, at this angle, with this force, where will the object end up, and how sure are we?

That question is one table row. The inputs are known before the push. The outputs are what TabPFN fills in. After each real push, the real answer becomes a new row, so the next prediction is better.

The doubts worth settling first

Tabular data is a snapshot. How can it describe motion?

Each row is a before → after record of one action: where the object was, how it was pushed, and how far it moved. The motion lives in the columns. For fast dynamics (a walking robot at 50 Hz) a row is one time step with velocities as columns. For pushing, one row per push is the natural unit.

To predict further ahead, do we feed predictions back in?

Yes, across pushes, not video frames. The predicted landing of push 1 becomes the input position of push 2. The spread grows each step. So we plan two or three pushes ahead, execute only the first, measure where the object really stopped, and plan again. That is model-predictive control.

A well-trained RL policy or VLA can handle many objects. So what is new?

You are right that it can, within its training. RL trained on randomized objects adapts to objects inside that range. VLAs generalize to objects they can recognize. Both struggle with hidden properties outside their training: weight, friction, an off-centre load, a worn motor. Fixing that means more training or a purpose-built adaptation module. TabPFN adapts from a few rows at run time, with no training, and says how sure it is.

So what exactly is the product?

A world model that learns on the job: given an object and a candidate push, it predicts where the object ends up, with a calibrated spread, and improves after every push. A planner, or a VLA, uses it to choose safe pushes. That covers the track's "where things are going" and "what happens next".

Why anyone outside the hackathon should care

Real robots meet new physics every day

Warehouses and parcels

Every parcel is a new object: unknown weight, contents and friction. Boxes that look the same weigh different amounts. The robot has seconds per item to adapt.

parcel · x · y · aim · force → dx · dy

Home and service robots

Mugs, bottles and toys on wood, glass or tablecloth. Nobody can simulate every home. The robot's first few pushes in that home are the data.

object · surface · aim · force → slide distance

Wear and damage

A gripper pad wears, a motor weakens, a wheel slips. Same robot, new physics. Today's rows overrule training-time assumptions without retraining.

command · joint state → actual motion

Field robots

On mud, sand or wet grass the same command moves a rover a different distance. It needs a calibrated "how far will this take me" before committing.

terrain features · command → displacement ± spread

The common thread

The physics changes after deployment, the change is invisible to cameras, real tries are scarce, and the robot must know when it is unsure. That is where a model that learns from a few rows, with calibrated uncertainty, earns its place next to RL and VLAs.

What we have to prove by Sunday 16:30

Claims we will measure, not assume

Hypotheses

  • On objects outside RL's training range, TabPFN reaches the target in fewer pushes.
  • Its 90% prediction bands contain about 90% of real outcomes.
  • Uncertainty-aware planning drops fewer objects.

Baselines

  • PPO trained on one object
  • PPO with randomized physics and history, the strong one, trained fast in JAX/MJX
  • MLP-ensemble world model given the same rows

Tests and risks

  • Held-out objects, hundreds of seeded episodes, confidence intervals
  • Decision latency with a cached context and batched candidates
  • Risk: push physics in MuJoCo is noisy, so we measure that noise first
