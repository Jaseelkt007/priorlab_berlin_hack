What TabPFN sees, what it predicts, and when

TabPFN never trains. It reads a table of examples recorded from the RL policy, then fills in one missing column for new rows. Here is exactly which table, which column, how many rows, and how its answer drives the physics.

Question 1

Where does the table in TabPFN's context come from?

From the trained RL policy. We let it fly 272 recorded flights in MuJoCo, six times with variations, and log every 0.2 ms step: what the fly sensed and what the policy did. Those logged steps are the examples TabPFN reads.

Question 2

What does one context row look like, and which column is the answer?

Each recorded step is unrolled into 12 rows, one per action. The rows share the same 104 sensor values and differ in one column, action_id. The last column, y, holds the policy's value for that action. That is the only column TabPFN ever predicts.

Question 3

At decision time: one row in, one row out, or many?

Twelve rows in, twelve numbers out. We take the fly's live sensors, copy them 12 times, set action_id to 0 … 11, and leave y empty. TabPFN fills in y for every row in one call. Read top to bottom, the 12 answers are the full action vector. This is the "same input, change one column" idea, with the action ID as the column we vary.

Question 4

When is TabPFN called, and does its answer drive the physics?

Yes, every control step. The 12 predicted actions go straight into MuJoCo, which advances the fly by 0.2 ms (four 0.05 ms physics steps). The new sensor reading becomes the next query. One second of flight is 5,000 TabPFN calls.

Question 5

What happens inside TabPFN during one call?

TabPFN is a transformer pre-trained on millions of synthetic tables. It treats every cell as a token, lets columns and rows attend to each other, and lets the query rows attend to the context rows, never the other way. The output for each query row is a distribution over y.

Question 7

Why 12 rows × 1 target column, and not 1 row × 12 target columns?

Both layouts ask the same question: given the 104 senses now, what are the 12 actions now? (Future positions are a different table, experiment A.) The difference is how the 12 answers are packed. TabPFN predicts one target column per model, so the "12 columns" layout really means 12 separate TabPFN models.

We have not measured which layout flies better; it is a quick offline test with experiment C (copy the policy's actions) and worth running before the final pitch.

Question 8

Is "one target column" a TabPFN limit, and what exactly is in a context row?

Yes, it is a limit: the TabPFN regressor predicts one target column per fitted model, with no built-in multi-target mode. That is why we add an action_id column and stack the 12 actions as 12 rows. Each context row holds 104 senses + 1 action_id as inputs, and 1 target, not 12 targets. It is still fully in-context: the rows are read and attended to, never trained on.

Your questions, one line each

Is the context from the RL policy?Yes. Every y in the context is the policy's action in that recorded state.
How many columns does TabPFN predict?One, called y. Which action it means is set by the action_id column.
One row in, one row out?Twelve in, twelve out, per decision. Same sensors, action_id 0 to 11.
Is it called at every step?Yes, every 0.2 ms of simulated flight: 5,000 calls per second of flight.
Does its output go into the physics engine?Yes, directly. The 12 values are the actions MuJoCo applies for the next 0.2 ms.
Does it predict several future steps?No, one step at a time. Future positions are a separate offline experiment (A).
Does the context change during flight?No. It is fitted once and cached; only the 12 query rows are new each step.
How big is the context?256 steps (3k rows) on a laptop; 16,384 steps (197k rows) on the H100, up to 1M rows tested.
