What TabPFN sees, what it predicts, and when

TabPFN never trains. It reads a table of examples recorded from the RL policy, then fills in one missing column for new rows. Here is exactly which table, which column, how many rows, and how its answer drives the physics.

Question 1

Where does the table in TabPFN's context come from?

From the trained RL policy. We let it fly 272 recorded flights in MuJoCo, six times with variations, and log every 0.2 ms step: what the fly sensed and what the policy did. Those logged steps are the examples TabPFN reads.

Question 2

What does one context row look like, and which column is the answer?

Each recorded step is unrolled into 12 rows, one per action. The rows share the same 104 sensor values and differ in one column, action_id. The last column, y, holds the policy's value for that action. That is the only column TabPFN ever predicts.

Question 3

At decision time: one row in, one row out, or many?

Twelve rows in, twelve numbers out. We take the fly's live sensors, copy them 12 times, set action_id to 0 … 11, and leave y empty. TabPFN fills in y for every row in one call. Read top to bottom, the 12 answers are the full action vector. This is the "same input, change one column" idea, with the action ID as the column we vary.

Question 4

When is TabPFN called, and does its answer drive the physics?

Yes, every control step. The 12 predicted actions go straight into MuJoCo, which advances the fly by 0.2 ms (four 0.05 ms physics steps). The new sensor reading becomes the next query. One second of flight is 5,000 TabPFN calls.

Question 5

What happens inside TabPFN during one call?

TabPFN is a transformer pre-trained on millions of synthetic tables. It treats every cell as a token, lets columns and rows attend to each other, and lets the query rows attend to the context rows, never the other way. The output for each query row is a distribution over y.
